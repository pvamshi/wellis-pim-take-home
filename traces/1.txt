❯ As you can see, we have legacy data with many problems and our objective for  
  this project is to build a web application that helps in importing legacy     
  data and also allows to take new patients intake.                             
  We will build this in iterative process where we start with importing the     
  legacy data and then new patient intake and then reviews for the new patients 
  at the end. As we build more features, we will do data migrations and code    
  upgrades we need to perform git commits frequently.                           
                                                                                
  To start with, we will brainstorm the ideas about how we want to handle this  
  project.                                                                      
                                                                                
  My main idea is to have a rules engine which is generated blindly from the    
  initial data structure and some feedback I give. Your job here is to          
  exhaustively come up with rules list.We would then apply these rules to the   
  legacy data and show it in the web application for review. Once the user      
  accepts the changes, the updates are added to the data and the data is        
  modified. Every modification needs a log to show which rule is applied and    
  what is the new structure. Once all the problems are resolved, that row is    
  eligible to be added to the main table this is the legacy migration process.  
  We will go into details. This is the main idea.                               
                                                                                
  User can give feedback for the rules, excluding some rows or declining a rule 
  and each action is accompanied with a comment on why the feedback is given.   
  AI will use workflow scripts and get that feedback and update the rules. This 
  way rules engine becomes a living engine that keeps improving with each user  
  feedback. AI will never applies a rule, it only creates a rule, and gets      
  feedback for the rule.

⏺ Understood, and filed at 1.1.2–1.1.4, 1.2, 1.5. Six things I'd want settled
  before this becomes a requirement.

  1. A read-only rule needs somewhere for its output to land.
     If a rule can't write, then the thing it produces is a proposal, not a
     change: row X, field Y, is A, should be B, because Z. The rule is a pure
     function; the runner persists what it returned. There's no table for that
     in your design yet, and it's the table everything else hangs off — the UI
     reads it, feedback attaches to it, acceptance consumes it, and promotion
     counts it.
  2. Does one rule both detect and fix?
     "Email is malformed" and "lowercase and trim it" are different claims. Some
     problems have one safe fix, some have several, some have none. The ones
     with none are exactly your review queue — a rule that finds a problem and
     says "I can't fix this, a human must". If a rule must always propose a
     value, you lose that category.
  3. What happens to rows a rule already changed when it goes to v2? [DECISION]
     This is the sharp one. Rule R v1 modified 400 rows. R v2 exists now. Those
     400 rows carry v1's decision, so the data no longer reflects the current
     ruleset — and the assignment demands a re-runnable importer.
     My recommendation: never mutate legacy rows in place. Keep the raw import
     immutable, and make the "current" row a derivation — raw plus the accepted
     proposals replayed over it. Then a version bump is a re-derivation, not a
     migration, and running the import twice is trivially idempotent because
     you're recomputing, not appending.
  4. How long does a row exclusion live?
     The user excludes row 123 from rule R with a reason. The workflow then
     rewrites R as v2 to handle that case properly. Does the exclusion carry to
     v2? If it does, you accumulate invisible carve-outs on a rule that looks
     clean. If it doesn't, a genuinely special-case row gets re-flagged every
     version. I'd treat an exclusion as evidence for the next version rather
     than a permanent carve-out — but it needs to be your call, and the answer
     changes the schema.
  5. Do rules see raw data only, or each other's output?
     If rules only ever read raw, ordering doesn't exist and the engine is
     simple — but a fix that depends on another fix becomes impossible
     (normalize the date, then dedupe on it). If rules see accepted proposals,
     you need an explicit ordering or pass structure. Simpler is genuinely
     defensible here; it just needs to be chosen, not discovered.
  6. Rule code keyed by (id, version) can never be deleted.
     The modification log points at a code key. Delete the code for (R, 1) and
     the history stops explaining itself. Also worth being deliberate about:
     because rules are code, a rule update is a deploy. That's a real cost, and
     it buys you rules that are reviewable, testable and in git — which for this
     assignment is the right trade, but it means "the engine keeps improving"
     happens at deploy cadence, not at runtime.

  One thing I'd push back on lightly: you don't have a concept for a finding
  that isn't anchored to a single row. "This patient exists in intakes but not
  in patients" belongs to a pair, not a row. Worth knowing whether that's in
  scope before the schema hardens.

  Question 4, restated. The user excludes row 123 from rule R, with a reason.
  The feedback workflow then reads that reason and rewrites R as version 2 so it
  handles that case properly. Does the exclusion carry over to version 2?

  If it carries, a rule that looks clean quietly accumulates carve-outs nobody
  sees when reading it. If it doesn't, a row that is genuinely special-case gets
  re-flagged every time the rule changes version. It's a schema question — the
  exclusion is either keyed to the rule or to the rule version.

  Two things your answers to 5 and 3 raised that I filed as open rather than
  deciding for you:

  - Rules re-run against modified data, and accepted changes are final. So what
    stops a re-run from re-proposing a change to a value a rule already fixed
    and the user already accepted — does the accepted proposal suppress that
    finding, or must the rule recognise its own prior output as already-correct?
  - Rules modify raw data in place, and the import has to be repeatable. If the
    import runs again over rows that were already fixed and accepted, the
    original CSV values would overwrite them. Avoiding that isn't the
    bidirectional-replay complexity you rejected — it's one landing table the
    import owns, and one working table the rules touch.

⏺ Six tables, at 1.6 — rule, rule_version, rule_run, finding, rule_feedback,
  modification.

  Three choices in there that are mine, not yours, and worth overruling if you
  disagree:

  1. Findings are disposable, modifications are permanent. A finding belongs to
     a run and the next run regenerates it. The modification log is the thing
     that never changes. This is what makes "Apply rules" cheap to press — it
     throws away working state, not history.
  2. Exclusions have no table of their own. An exclusion is a row in
     rule_feedback with kind: 'exclude_row'. The runner joins against it to know
     what to skip. A separate rule_exclusion table would mean the same fact
     stored twice.
  3. Ambiguous findings are the same table, with newValue: null. A rule that
     spots a problem but has no fix writes a finding with no new value and an
     explanation. No second table, no second code path.

  The one thing the schema can't settle on its own is 1.2.a — what a declined
  proposal becomes. Right now a decline sets the rule inactive, so the rule
  stops running and its findings stop appearing. That works for declining a
  rule. It does nothing for declining a single row's change while keeping the
  rule, which your UI doesn't currently offer — approve and decline are both
  rule-level, and the only per-row action is exclude. Worth knowing whether
  that's intentional before I write the entities.

⏺ Concrete case — rule R7, "normalise Dutch phone numbers to +31".

  - P-0817 has 0032 475 123456 — a Belgian number. v1 proposes +310032475123456.
    Wrong.
  - P-0455 has 000000000 — junk, not a phone at all. v1 proposes +3100000000.
    Also wrong, but for a completely different reason.

  You cross out both. On P-0817 you tick the checkbox with "0032 is a country
  code, not a leading zero". On P-0455 you leave it unticked: "placeholder
  garbage, we'll deal with it separately".

  The workflow writes v2, which treats 00<country> as international. You press
  Apply rules.

  If the key includes version — (row, rule, version, column) — v2 writes a fresh
  pending row for P-0817 proposing +32475123456. That's exactly what you asked
  for. But it also re-proposes on P-0455, and you decline it again. And again on
  v3, and v4.

  If the key excludes version — (row, rule, column) — P-0455 stays declined,
  correct. But P-0817 also stays declined, so v2 is blocked from making the very
  fix it was written to make. The rule rewrite accomplishes nothing.

  Neither key works alone, because the two crosses meant different things.
  P-0817 was "this rule is wrong, fix it". P-0455 was "this row is wrong, leave
  it alone forever".

  Which is what the checkbox already distinguishes — it just needs to control
  the decline's scope, not only trigger a rule rewrite. Ticked: the decline
  applies to this version only, and the next version re-asks. Unticked: the
  decline applies to the rule permanently, and no future version ever proposes
  on that row again.

  So the key stays (row, rule, version, column), and the declined row carries
  whether the decline was version-scoped or permanent.

  One question. What makes two files "the same file" — the filename, or the
  contents?

  It matters because the two answers behave oppositely on the case you'll
  actually hit. If it's the filename, then a corrected re-export of patients.csv
  is "the same file", so the importer skips it entirely and none of the
  corrections land. If it's a content hash, that re-export is a new file, so
  every id in it is already known and every row gets declined by 1.0.2 — which
  also lands nothing, but for the opposite reason.

  Re-running the identical file works either way. It's the corrected re-export
  that needs the answer.

❯ pound-tokg constraint ?                                                       

⏺ A patient row has weight = 180 and weight_unit = lbs. The fix is weight = 81.6
  and weight_unit = kg.

  That's one decision but two columns, and the requirements can't express it:

  - 1.1.5 says a rule changes the column it tested. To know 180 is pounds you
    read weight_unit; to fix it you write weight. Tests one, changes the other.
  - 1.1.4 says one rule, one fix — so you can't call it two rules either without
    the value and the unit being approved separately, and either one alone
    leaves the row wrong.

  The option that obeys both is to ignore weight_unit and infer pounds from the
  number — anything over ~200 is probably pounds. It's single-column, atomic and
  self-terminating. But it guesses, and it leaves weight_unit still saying lbs
  on a value that's now kilograms.

  What I'd do: read 1.1.4's "one fix" as one decision, not one column. A rule
  declares the columns it changes on that row, they're written in the same
  transaction, and you approve them as one thing. Self-termination still holds
  because after the fix weight_unit says kg and the rule stops matching.

  That's a change to 1.1.4 and 1.1.5, which is why I didn't make it.
