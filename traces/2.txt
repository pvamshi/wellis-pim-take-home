❯ would it be faster if we skip tests                                           

⏺ No. Tests aren't what's slow — three serial agent handoffs per rule are, and
  the tests are a small slice of one of them.

  1. What the time actually goes on. Each rule spins up a dev agent, then a
     review agent, then a land agent, each with its own context to build up
     before it does anything. Writing a spec is maybe a quarter of the dev
     agent's work. Running it is seconds.
  2. Skipping tests costs more than it saves. The review agent's verdict
     currently rests on something objective — the spec asserts the proposed
     value, not just that the rule fired. Take that away and review becomes
     "read it and reason about it", which is slower per rule and wrong more
     often. A rule that fails review costs a full extra dev+review cycle, which
     dwarfs what the spec saved.
  3. The real lever is batching. One dev agent doing P25–P32 in a single
     context, then one review, then one commit per batch. That kills most of the
     per-rule spin-up. It weakens your resume guarantee from per-rule to
     per-batch, which is still fine for stopping mid-run. [DECISION] — batch
     size is yours; 5–8 keeps a lost batch cheap.
  4. Cheaper cut if you want one. just rules-sync re-runs nest build after the
     dev and review agents have each already built. Three full Nest builds per
     rule. That's dead weight the tests aren't.

❯ its also tokens, too many are being spent .                                   

⏺ The tokens go on re-reading, not on writing. Three fresh agents per rule × 122
  rules is 366 contexts, and each one boots by reading the same 122-row
  catalogue, the same requirements file, the same deferred list, and an existing
  rule as an example — to produce about fifteen lines of code.

  1. Inline the catalogue row. The workflow already knows which rule id it's
     building. Pulling that one table row out of the markdown and putting it in
     the prompt means no agent ever opens the 122-row file. That alone removes
     the single largest repeated read, three times per rule.
  2. Batch. Same fix as for speed, bigger effect on tokens: one dev context
     covering eight rules pays the preamble once instead of eight times, and it
     already has the example rule in context after the first one.
  3. Stop the review agent re-running the build. It runs just build and just 
     test immediately after the dev agent did, and reads both outputs in full.
     The test output grows every rule. Having it read only the diff and the test
     result summary keeps the independence without paying for the transcript
     twice.
  4. Model. Dev and review are running on Opus for mechanical work — a table row
     in, a small pure function and a spec out. Sonnet handles this shape, and
     the review agent's job is comparison against an entry that's now inline in
     its prompt.

  [DECISION] 1 and 3 are safe to do mid-run. 2 and 4 change the shape of what's
  already in flight, so they'd want the current P16–P40 run finished or stopped
  first.

  Four things changed, and the largest is the one you'd least expect:

  1. The rules landed so far average ~500 lines each for about 40 lines of 
     logic. P30 is a 200-line doc comment enumerating every case the code
     already states. That output was the biggest single spend, and every later
     agent then paid to read one as its example. There's now a 15-line comment
     budget and an 80-line spec budget, with the comment still required to state
     what it catches, what it proposes, why the ambiguity flag, the boundary
     against neighbouring rules, and why an approved row stops matching — once
     each.
  2. No agent opens the notes any more. The six binding requirements are written
     into the prompt, a complete example rule is inline, and a grep pulls only
     the batch's table rows plus the headings that place them. That removes
     three large reads per rule.
  3. Six rules per dev context, one review per batch reading the diff rather
     than re-running the build, one rules-sync per batch instead of per rule.
     Commits stay per-rule, so history and resume are unchanged — the resume
     unit is now the batch.
  4. All three stages on Sonnet.

  read inconsistently unless you want them trimmed later. And P41–P48 turned out
  not to be blocked — nothing in the weight rules spans two columns; the

  bug.

  Approve would try to write the proposed value into the column, but an
  ambiguous rule proposes nothing. The backend catches it and refuses with "it
  proposes no value", so no data is touched; the press just errors. Nothing is
  erased — the guard is explicit about why, since there's no undo for an
  accepted change.

  Decline on those rows is meaningful: it's how you say this row isn't a
  problem, and it's remembered for every future version of that rule. So is the
  revise checkbox — for an ambiguous rule that's the whole point of the screen,
  since there's nothing to accept.

  [DECISION] Two ways to fix the tick: hide it on ambiguous rules entirely, or
  keep it and have it mean "I've looked at this, stop showing it to me" — which
  is what decline already does. Hiding it is the honest one; the screen then
  offers exactly the two actions that exist.

  workflow is now building it: five tasks, one after another. Here's what it
  covers:

     find. A pair gets one link only, and a link you dismiss won't come back on
     later runs.

     version that names the two actual rows, not just their legacy ids. The old
     versions stay registered but switched off.
  3. Confirm and dismiss, with a screen. It lists links, shows both rows side by
     side with the differences highlighted, and has Confirm and Dismiss
     buttons.
  4. Retiring X. Confirming a patient link marks X as Import rejected, with the
     reason naming Y. You can undo that like any other rejection. This was
     deferred item D5, and it can be built now because rows have a rejected
     state. For intakes and consents both rows share one id, so nothing gets
     rejected. Accepting import rows instead skips the confirmed duplicate.
  5. Merging. Seven new rules, one per column, fill an empty column on Y with
     X's value. They only cover facts about the person: name, email, date of
     birth, sex, citizen number, phone and city. Signup date, source, status,
     weight and height stay as they are, since they describe a particular signup
